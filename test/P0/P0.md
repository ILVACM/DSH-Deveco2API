## 1. 为什么先写 P0

整条链路有 **4 个可能致命的不确定性**，全都在 P0 一次性暴露，不要等到写插件时才发现：

| # | 不确定性 | 若到后期才发现 |
| --- | --- | --- |
| 1 | 双层 AES-256-GCM 能不能解开 | 插件核心逻辑全部作废 |
| 2 | access token 过期后能否刷新 | 只能用 30 分钟，无法长期运行 |
| 3 | 上游到底是不是 OpenAI 兼容、流式帧长什么样 | wire 层要重写 |
| 4 | 错误到底是 HTTP 200 还是 4xx | 错误处理层要重写 |

**P0 通过 = 这四件事全部有确定答案。**

## 2. 一键运行（零依赖）

```bash
cd D:\dsh-deveco2api
node test/P0/probe.ts
```

**不需要 `npm install`，不需要 pnpm，不需要构建。** 只用 Node 内建模块：

| 用途 | 模块 |
| --- | --- |
| 文件读写 | `node:fs/promises`、`node:fs` |
| 路径 | `node:path`、`node:os` |
| 解密 | `node:crypto`（`createDecipheriv`） |
| 哈希 | `node:crypto`（`createHash`） |
| HTTP | 全局 `fetch`（Node 18+ 内建） |
| 超时 | `AbortSignal.timeout()`（Node 17.3+ 内建） |

已验证：本机 Node **v24.21.0** 原生支持直接执行 `.ts`（类型剥离），且 `fetch` / `ReadableStream` / `AbortSignal.timeout` 全部可用。

### 可选参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--only=N[,M]` | 全部 | 只跑指定编号的检查（如 `--only=1,2,3`），便于分段调试 |
| `--write` | **关闭** | 刷新成功后**写回** `auth.json`。默认只在内存里用，不碰磁盘 |
| `--model=GLM-5.3` | `GLM-5.1` | 指定对话测试用的模型 |
| `--verbose` | 关闭 | 打印完整 SSE 帧与完整 JSON |
| `--no-color` | 自动 | 管道/重定向时自动关闭 ANSI 颜色 |

### 四种结果状态（不要只有 PASS/FAIL）

| 状态 | 含义 | 计入失败？ |
| --- | --- | --- |
| `PASS` | 符合期望 | ❌ |
| `FAIL` | 不符期望 | ✅ |
| `SKIP` | 前置条件不满足（如 token 未过期、`--only` 跳过） | ❌ |
| `INFO` | 只记录不断言（如 6b 思考通路、7a 负向用例） | ❌ |

**汇总表分别统计 `PASS / FAIL / SKIP / INFO` 四项**，总判定只看 `FAIL` 数量：`FAIL == 0` 即通过。

> 只有 PASS/FAIL 两态时，「token 还没过期所以没刷新」会被误判成失败——这就是加 SKIP 的原因。

## 4. 八项检查清单

### [1] 环境自检

**验什么**：Node 能力、凭据文件是否齐备。

**期望**：
- `node` ≥ 22（类型剥离 + 内建 fetch）
- `fetch` / `ReadableStream` / `AbortSignal.timeout` 三者存在
- 以下文件全部存在：

| 文件 | 路径 | 必需 |
| --- | --- | --- |
| `auth.json` | `%USERPROFILE%\.local\share\deveco\auth.json` | ✅ |
| `token.enc` | `%USERPROFILE%\.config\deveco\token.enc` | ✅（刷新要用） |
| `token.dek` | `%USERPROFILE%\.config\deveco\token.dek` | ✅ |
| `keys/<kekId>.bin` | `%USERPROFILE%\.config\deveco\keys\` | ✅（**文件名从 `token.dek` 的 `kekId` 字段读，不硬编码**） |

> ⚠️ **不要硬编码 `kek-v1.bin`**。本机现在恰好是 `kek-v1`，但源码支持 `kek-v1/v2/v3` 三套轮换（`local-crypto.ts:31`），
> 正确做法是：先读 `token.dek` 拿到 `kekId`，再去 `keys/<kekId>.bin` 取密钥。若该文件缺失 → FAIL 并明确提示「密钥文件缺失或已轮换」。

**失败时**：缺 `auth.json` → 说明没登录，跑 `deveco auth login`。

---

### [2] 解包 DEK（KEK → DEK）

**验什么**：`token.dek` 能被 `keys/kek-*.bin` 解开。

**算法**（对齐 DevEco Code `security/local-crypto.ts:82-90` 的 `unwrapDek` 逻辑；上游源码快照已移除，本文件已给出完整算法，不依赖快照）：

```
wrapped = JSON.parse(token.dek)
  { version, algorithm:"aes-256-gcm", kekId, encryptedDek, iv, authTag, timeStamp }
kek  = readFile(`keys/${wrapped.kekId}.bin`)          // 32 字节
dec  = createDecipheriv('aes-256-gcm', kek, b64(wrapped.iv))
dec.setAuthTag(b64(wrapped.authTag))
dek  = dec.update(b64(wrapped.encryptedDek)) + dec.final()   // 32 字节
```

**期望**：`kekId` 为 `kek-v1` / `kek-v2` / `kek-v3` 之一（**以 `token.dek` 实际值为准，不要断言具体是哪个**），`kek` 32 字节，`dek` 32 字节。

**失败时**：`authTag` 校验错 → 密钥文件被换过，需重新登录。

---

### [3] 解密 access token

**验什么**：`auth.json` 里的 `deveco.access` 能被 DEK 解开。

**算法**（对齐 `local-crypto.ts:127-139`、`:189-196`）：

```
blob = auth.json.deveco.access
  { version, algorithm, ciphertext, iv, authTag, timeStamp }
dec  = createDecipheriv('aes-256-gcm', dek, b64(blob.iv))
dec.setAuthTag(b64(blob.authTag))
access = dec.update(b64(blob.ciphertext)) + dec.final()
```

**同时读出明文旁证**（这些字段不加密）：
- `deveco.expires`（数字，毫秒时间戳）
- `deveco.isRealName`（布尔）
- `deveco.type`（应为 `"oauth"`）

**期望**：`access` 长度约 136；`refresh` 解出来是**空字符串**（本机实测如此，不是异常）；`isRealName` = `true`。

---

### [4] token 有效性判定 + 刷新

**验什么**：过期后能否拿到新 token，且新 token 真的能用。

**判定**：
```
now < expires  → SKIP（token 仍有效，不刷新；不视为失败）
now ≥ expires  → 走刷新
```

> 实测补充（2026-11-03）：`expires` 是**明文**字段，可直接读；`deveco` CLI 每次运行都会刷新并更新它，
> 所以「刚跑过 CLI 就马上跑探针」大概率会命中 SKIP —— **这是正常现象，不是脚本坏了**。

**刷新**（对齐 `login-service.ts:382-422`）：

```
GET https://cn.devecostudio.huawei.com/authrouter/auth/api/jwToken/check
header: refresh: "true"
header: jwtToken: <从 token.enc 解出的 JWT>
→ 200 { status, userInfo: { accessToken, refreshToken, nationalCode, realName } }
```

注意：JWT 本身要从 `token.enc` 解（用 DEK），与 `auth.json` 是两份文件。

**期望**：
- `status: true`
- `userInfo.accessToken` 存在
- `nationalCode: "CN"`
- `realName: true`

**写回策略**：
- 默认**不写回**（`--write` 才写），只在内存里替换，供 [5][6][7] 使用
- 若 `--write`：先备份 `auth.json` → `auth.json.p0bak`，写入时校验磁盘上 `access` 仍等于旧值（CAS），不等则放弃写入并报 WARN

**失败时**：`status:false` → JWT 过期，需 `deveco auth login`。

---

### [5] 拉取模型目录

**验什么**：目录端点可用、解析正确、blacklist 生效。

```
GET https://cn.devecostudio.huawei.com/codeGenie/modelConfig?localVersion=0&pluginVersion=CLI.<ver>
header: Authorization: Bearer <access>
```

`<ver>` 取 `deveco --version` 的输出（本机 `0.3.0-stable`），拿不到就用 `0.0.0`。

> **实测（2026-11-04）：`pluginVersion` 参数完全不敏感。**
> `CLI.0.3.0-stable` / `CLI.0.0.0` / `CLI.`（空）三者返回**完全相同**（同 932 字节、同 3 个模型）。
> 因此版本探测降级为 **best-effort**：优先读 `@deveco/deveco-code/package.json` 的 `version`（快且无警告），
> 失败再尝试 `deveco --version`，最后兜底 `0.0.0`。探测失败不影响本项判定。

**解析**（对齐 `deveco-models.ts:102-232`）：
```
body.inner_models[] → { protocol, group_name, model_configs[], task_default_model_map? }
model_configs[]     → { id, model_id, thinking_mode, context_window, output,
                        tool_call_mode, input_modalities, reasoning_effort }
blacklist           → task_default_model_map["blacklist"]（逗号分隔的 model_id）
```

**期望**（本机实测快照，可能随上游变化）：

| 项 | 期望 |
| --- | --- |
| `code` | `200` |
| `version` | 数字（实测 15） |
| 模型总数 | 3 |
| 模型列表 | `GLM-5.3`、`GLM-5.1`、`Qwen3_VL_235B_A22B_Instruct` |
| `blacklist` | 含 `Qwen3_VL_235B_A22B_Instruct` |
| **暴露数** | **2**（blacklist 里的不算） |
| `small_model` | `GLM-5.3` |

> 判定规则：只要「暴露数 ≥ 1」且「含 GLM-5.1 或 GLM-5.3」即 PASS。模型名随上游轮换，**不要硬断言具体 id**，只断言「有模型且 blacklist 生效」。
>
> ⚠️ **本项产出的「暴露列表」是 P1 模型白名单的唯一来源**——因为 [8c] 已证明上游对未知模型不校验（会静默回落）。

### [6] 流式对话（两个子用例）

**验什么**：真能拿到 token 流；**并且确定「思考内容」到底走哪个字段、会不会吃掉输出预算**。

> ⚠️ 这一节是 P0 里**最容易误判**的一项。实测已经发现：**`thinking` 字段决定思考内容出不出现，而思考会吃掉 `max_tokens`**，稍不注意就会得到「HTTP 200 但正文全空」的假失败。因此必须拆成两个子用例。

#### 6a —— 不传 `thinking`（基础通路）

```
POST https://cn.devecostudio.huawei.com/sse/codeGenie/maas/v2/chat/completions
headers:
  authorization: Bearer <access>
  content-type : application/json   ← 必需（缺失 → 400）
  Chat-Id      : <32 hex>            ← 必需（只校验存在性）
  Session-Id   : <32 hex>            ← 可选
  lang         : en                  ← 可选
body:
  { model, messages:[{role:'user',content:'只回复两个字：可用'}],
    stream:true, max_tokens:256 }    ← 不传 thinking
```

> **最小必需头**（实测 2026-11-04）：`authorization` + `Chat-Id` + `content-type` 三件套即可通过；
> 缺 `content-type` 也会 400；`Chat-Id` 只校验**存在性**（8 字符也能过），不校验格式；`lang` / `Session-Id` 均可省。

**期望**：HTTP 200 + `text/event-stream`；`delta.content` 有正文；`finish_reason` 为 `stop`；末尾 `data: [DONE]`。

> ⚠️ **`max_tokens` 不能写死 32**（实测 2026-11-04）：`GLM-5.3` 即使不传 `thinking` 也会输出大段内部推理，
> 32 token 会被吃满（`finish=length`，正文被截断）。128 以上才稳定收尾。探针统一用 **256**。
>
> ⚠️ **`GLM-5.3` 会把内部推理泄漏进 `content`**：实测请求「只回复两个字」得到 527 token 的 `content`，
> 内含 `This is a harmless request… </think>可用`。探针会检测 `think` 标签并在报告里标 `⚠ 泄漏`。
> **P1 的 adapter 必须剥离 `</think>` 之前的内容。**

#### 6b —— 传 `thinking:{type:'enabled'}`（思考通路）

同一 prompt（改用推理题），body 增加 `thinking:{type:'enabled'}`，`max_tokens` 提到 **512**。

**期望**：出现 `delta.reasoning_content` 增量；且**记录下 `finish_reason` 与「正文是否为空」**。

> **实测结论（2026-11-03 / 11-04，本机）**：
>
> | 用例 | 模型 | max_tokens | thinking | 正文长度 | 思考长度 | finish |
> | --- | --- | --- | --- | --- | --- | --- |
> | 6a 短问 | GLM-5.1 | 32 | 不传 | 2（`"可用"`） | 0 | `stop` |
> | 6a 短问 | GLM-5.3 | 32 | 不传 | 138 | 0 | `length` ✗ |
> | 6a 短问 | GLM-5.3 | 128 | 不传 | 461 | 0 | `stop` ✓ |
> | 6b 推理题 | GLM-5.1 | 32 | `enabled` | **0** | 54 | `length` |
> | 6b 推理题 | GLM-5.1 | 512 | `enabled` | **0** | 436 | `length` |
> | 6a 推理题 | GLM-5.1 | 32 | 不传 | 63 | 0 | `length` |
>
> 即：**开思考后，思考内容会耗尽整个 `max_tokens` 预算，导致 `content` 为空**（这与 opencode2dsh 的 `reasoning-recovery` 场景完全对应）。而 `reasoning_effort:'low'` / `'none'` 实测**不能**避免这一点。
>
> 因此：
> - **6a 必须 PASS**（基础通路）
> - **6b 只记录不断言**：只要观察到 `reasoning_content` 字段存在即算"通道支持思考"，**不要求正文非空**
> - 报告里必须记录这张表，供 P4 决定「思考耗尽预算时是否重试」

#### 通用断言（6a/6b 都检查）

| 项 | 期望 |
| --- | --- |
| HTTP | `200` |
| `content-type` | `text/event-stream` |
| 帧数 | ≥ 3 |
| 首帧延迟 | < 30000 ms |
| 每帧带 `usage` | ✓（DevEco 特征，非标准） |
| 帧前有 `id: N` 行 | ✓（DevEco 特征，非标准） |
| 终止 | 出现 `data: [DONE]` |

**失败时**：
- `429` + `FreeUsageLimitException` → 配额耗尽，稍后重试
- `200` 但首帧是 `event: error` → 见 [8]，把错误原文打出来
- `200` 且 `content` 为空但 `reasoning_content` 有内容 → **不是失败**，是「思考耗尽预算」，按 6b 记录

### [8] 错误形态识别

**验什么**：把三种"非标准"上游行为的实际报文固化下来，供 P4 的错误分类器与 P1 的白名单逻辑做断言基准。

**8a —— 坏 token（断言）**
```
POST /chat/completions  +  authorization: Bearer badtoken  +  Chat-Id
```
期望：**HTTP 200** + 裸 JSON `{"errorCode":4016,"errorMsg":"invalid accessToken.",...}`
（注意：不是 401，也没有 `error` 字段）

**8b —— 缺 Chat-Id（断言）**
```
POST /chat/completions  +  authorization: Bearer <真 token>  +  不带 Chat-Id
```
期望：**HTTP 400** + `{"error":{"type":"BadRequest","param":{"originalMessage":"SSE request missing header:Chat-Id"},...}}`

**8c —— 未知模型（INFO，重大发现）**
```
POST /chat/completions  +  model: 'p0-probe-nonexistent-model'  +  max_tokens: 64
```
期望：**HTTP 200** + 回显 model 为 `deepseek-v4-flash` + 正常输出正文

> ⚠️ **这是 P0 最重要的安全发现**：上游对**不存在的模型名**不做校验，直接静默回落到 `deepseek-v4-flash` 并正常出结果。
>
> 后果：如果插件把用户选的模型名原样透传给上游，模型拼错或已下架时**不会报错**，而是静默用另一个模型回答——用户以为在用 A 模型，实际在用 B。
>
> **对策（P1 必须做）**：插件侧建立**模型白名单**（来源是 [5] 拉到的 `modelConfig` 暴露列表），请求前校验模型名，不在白名单里直接拒绝，绝不把校验权交给上游。
>
> 注：该行为**偶发不稳定**（实测约 1/5 概率命中排队，返回 `bytes=204` 的空帧），因此探针把它记为 **INFO** 而非 FAIL；
> 明细里会注明「本次可能命中排队/截断，属偶发」。

> 8a / 8b 是 P4 `errors.ts` 的黄金测试用例，8c 是 P1 模型白名单的依据；P0 就把三者原样存进报告 JSON。

## 5. 安全边界（必须遵守）

| 约束 | 做法 |
| --- | --- |
| **绝不打印完整 token** | 只打印前 8 位 + 后 4 位 + 长度（如 `eyJhbGci...f3a9 (len 136)`） |
| **绝不写入凭据目录**（默认） | 刷新只在内存中生效；`--write` 才写，且先备份 + CAS 校验 |
| **绝不修改 `token.enc` / `keys/`** | 全程只读 |
| **报告文件不含密钥** | `p0-report.json` 只存长度、时间戳、模型名、错误码 |
| **失败不重试轰炸** | 每个网络请求只发一次，`AbortSignal.timeout(30s)` |

   **协议层（4 条）**

   - 流式帧的真实结构：`id: N` + `data:` 交替，**每帧都带 `usage`**（非标准 OpenAI 格式）
   - 非流式必须改写路径：`/chat/completions` + `stream:false` 会失败，必须走 `/no-stream/chat/completions`

   **思考与预算（2 条）**

   - 思考内容走 `delta.reasoning_content`，且**需要显式传 `thinking:{type:'enabled'}` 才出现**
   - 思考会吃满 `max_tokens` 导致 `content` 为空（附四组对照数据）

   **模型行为（2 条，2026-11-04 补充）**

   - **`GLM-5.3` 会把内部推理泄漏进 `content`（带 `</think>` 标签），且不传 `thinking` 也会发生**
     → 实测：请求「只回复两个字」得到 527 token 的 `content`，内含 `This is a harmless request… </think>可用`
     → 影响：P1 的 adapter 必须剥离 `</think>` 之前的内容，否则用户会看到模型的内心独白
   - **输出预算必须按模型自适应，不能写死**
     → 实测对照：

       | 模型 | `max_tokens=32` | `max_tokens=128` |
       | --- | --- | --- |
       | `GLM-5.1` | `content=2`，`finish=stop` ✓ | 同样正常 |
       | `GLM-5.3` | `content=138`，`finish=length` ✗ | `content=461`，`finish=stop` ✓ |

     → 影响：探针用 `256`（6a）/ `512`（6b）；P1 的默认输出预算不能低于 128

   **上游行为（1 条，2026-11-04 新增）**

   - **未知模型会被静默回落**：请求 `p0-probe-nonexistent-model` 得到 HTTP 200 且回显 `deepseek-v4-flash` 并正常输出正文

     → 注：该行为偶发不稳定（约 1/5 概率命中排队返回空帧），因此探针把它记为 INFO 而非 FAIL

5. `probe.ts` 里的解密函数与请求函数**可直接搬到 `packages/plugin/src/`**（无 `console.log` 污染、无硬编码路径）
6. `P0.md`、`probe.ts`、`runs/` 三者同目录，可随 commit 一起留档

### 实现约定

| 约定 | 说明 |
| --- | --- |
| **每步独立可跑** | 后面的步骤依赖前面产出的中间值（如 `dek`、`access`）；`--only` 跑后段时，前段会被静默补齐但不输出 |
